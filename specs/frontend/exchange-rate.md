# Exchange Rate Sync — Frontend Spec

## Overview
A page under the "匯率中心" sidebar group (label `匯率同步`, route `/exchange-rates`, already an enabled nav item). Shows, per brand, the most recently synced rate for every global currency pair definition as three values — 原始匯率 (the plain provider rate), 入金匯率, 出金匯率 (that brand's deposit/withdrawal rate as it stood at the moment of the last sync, not recomputed live) — lets an admin trigger a fresh sync covering every brand at once (60-second cooldown between syncs), and lets them search/filter the visible table by base or quote currency code. This page reads point differential values (入金/出金匯率) but never configures them — 點差 itself is still only ever set on the existing 價差群組管理 page (品牌預設點差／點差群組); a brand currency pair with no group simply uses its brand's default. Backed entirely by [exchange-rate.md](../backend/exchange-rate.md). Managing a brand's own rate/spread *settings* remains exclusively on the separate `品牌幣種對`/`價差群組管理` pages — this page must never re-implement or shadow any part of that, it only displays a historical snapshot.

## Requirements

### Page: 匯率同步 (`/exchange-rates`)
- On load, calls `GET /api/brands` and renders a brand selector (tabs, matching `品牌幣種對`'s pattern) listing all 7 brands by `code`. The first brand is selected by default.
- Selecting a brand calls `GET /api/exchange-rates/latest?brandId={id}` and renders one row per currency pair definition for that brand.
- A `搜尋基準幣或報價幣` text input sits above the table. Typing filters the already-loaded rows client-side (no extra API call) to those whose `baseCurrencyCode` or `quoteCurrencyCode` contains the typed text, case-insensitive substring match, live as the user types. Clearing the input shows every row again. Filtering never triggers a reload and is independent of the brand selection or the sync button/cooldown state.
- Table columns: `基準幣`/`報價幣` (monospace currency code), `原始匯率` (formatted `rate`, or "尚未同步" if `null`), `入金匯率` (formatted `depositRate`, bold, or "-" if `null`), `出金匯率` (formatted `withdrawalRate`, bold, or "-" if `null`), `匯率時間` (`rateMinute` formatted `YYYY-MM-DD HH:mm`, or "-" if `null`), `資料來源` (`source`, or "-" if `null`). No 點差 input of any kind — 入金匯率/出金匯率 are read-only, already-computed snapshot values from the last sync, not editable here.
- `同步最新匯率` button (one global action, not scoped to the selected brand — it syncs every brand at once):
  - On click: disable the button and change its label to `同步中...`, call `POST /api/exchange-rates/sync` with no request body.
  - On success (`200`): reload the table for the currently selected brand via `GET /api/exchange-rates/latest?brandId={id}` (re-apply whatever search text is currently in the filter input to the freshly loaded rows), show a success toast reflecting the *total* sync scope across all brands (`已同步 {updated.length} 筆匯率` when `skipped` is empty, `已同步 {updated.length} 筆匯率，{skipped.length} 筆供應商未提供報價` when not), then start a 60-second cooldown: the button stays disabled with its label counting down (`60 秒後可同步` → `59 秒後可同步` → ... → back to `同步最新匯率` and enabled at 0).
  - On failure with `429` (cooldown rejected by the server — e.g. a stale client-side timer, another tab, or a page reload mid-cooldown): show an error toast (`同步失敗，請稍後再試` is NOT used here — show the response's own message, e.g. `匯率同步一分鐘內僅能執行一次，請稍後再試`) and immediately (re)start the button's countdown from the response's `retryAfterSeconds` instead of a fresh 60.
  - On failure with `502` or a network error: re-enable the button immediately (no cooldown — the server didn't actually sync), show an error toast (`同步失敗，請稍後再試`); the table keeps its previous contents (not cleared).
  - The client-side countdown is a UX convenience only, reset per page load (a freshly loaded page always starts with the button enabled) — the server's own 60-second check via `429` is the actual source of truth and is what's exercised by the acceptance criteria below, not just the client timer.
- Switching the selected brand does not affect the sync button's in-flight/cooldown state (it's global) — only which brand's rows the table currently shows.
- The search input is never disabled by sync/cooldown state — a user can filter the table at any time, including while a sync is in flight or during the cooldown countdown.
- No create/edit/delete controls, no per-row actions, no rate-type/active/spread-group columns, and no connection to the audited per-brand spread system's *write* path anywhere on this page — the brand selector exists only to pick whose snapshot to view.

## API Integration
| Action | Method | Path | Request | Response |
|---|---|---|---|---|
| 載入品牌清單（選擇器用） | GET | /api/brands | — | `[{id, code, name, active, ...}]` |
| 載入某品牌的目前匯率清單 | GET | /api/exchange-rates/latest?brandId={id} | — | `[{currencyPairDefinitionId, baseCurrencyCode, quoteCurrencyCode, precision, brandId, brandCode, rate, depositRate, withdrawalRate, rateMinute, source}]` |
| 同步最新匯率 | POST | /api/exchange-rates/sync | — (no body) | `{syncedAt, updated: [{currencyPairDefinitionId, baseCurrencyCode, quoteCurrencyCode, brandId, brandCode, rate, depositRate, withdrawalRate}], skipped: [{currencyPairDefinitionId, baseCurrencyCode, quoteCurrencyCode, reason}]}` or `502 {error}` or `429 {error, retryAfterSeconds}` |

The 基準幣/報價幣 search is entirely client-side filtering over the array `GET /api/exchange-rates/latest?brandId={id}` already returns — it is not a query parameter and does not make a separate network call. `updated.length`/`skipped.length` used in the sync toast are the full response's counts across every brand, not filtered to the currently selected one.

## Error States
- Brand selector load failure: inline error message with a `重試` button instead of the selector/table.
- Currency rate list load failure (for the selected brand): same pattern, scoped to the table area (same as `幣別對管理`/`品牌幣種對`).
- Sync failure (`502`/network): error toast per above; page stays on whatever it last successfully loaded; button re-enabled immediately.
- Sync failure (`429`): error toast showing the server's message; button stays disabled, cooldown countdown (re)started from `retryAfterSeconds`.
