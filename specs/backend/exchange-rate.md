# Exchange Rate Sync — Backend Spec

## Overview
Reads current market rates from a free, key-less external provider, and for every [currency pair definition](currency-pair-definition.md) fans out across every existing brand, storing one snapshot per (definition, brand) per minute (see [exchange-rate.md](../dba/exchange-rate.md)): the plain provider rate (`rate`, 原始匯率, identical for every brand under the same definition), plus that brand's own `depositRate`/`withdrawalRate`（入金/出金匯率）computed at that exact moment by multiplying the plain rate by `(1 + spreadPercent / 100)` using the brand's then-currently-effective spread percentage — a percentage markup, not a flat amount added. This reuses the exact same effective-spread resolution [currency-pair.md](currency-pair.md)'s `GET /api/currency-pairs` already implements for its own live `depositRate`/`withdrawalRate` (group's spread percentage if the brand's pair is assigned to one, otherwise the brand's default from [spread.md](spread.md)) — the difference is purely *when* it's computed: `currency-pair.md`'s version recalculates on every read using today's spread config, while this one is computed once at sync time and frozen into history — a later spread change never rewrites a past `exchange_rate` row. Writes here are not routed through the audit/approval module (see [audit.md](audit.md)): a market data sync is a system action, not a brand-facing configuration change.

External provider: **open.er-api.com** (free, no API key, broad ISO 4217 coverage). `GET https://open.er-api.com/v6/latest/{baseCode}` returns every other currency's rate against `{baseCode}` in one call: `{ "result": "success", "base_code": "USD", "rates": { "JPY": 149.85, "TWD": 31.25, ... }, ... }`.

To prevent hammering the external provider, a sync is rejected outright if the last **successful** sync (one that actually upserted at least one row, for any definition/brand) happened less than 60 real-world seconds ago — this is independent of `rateMinute`'s minute-bucketing, which only governs upsert-vs-insert within one already-accepted sync. The cooldown is global (not per-brand): one button, one sync, covering every definition × every brand in a single call.

## Requirements

### Entity: ExchangeRate
| Field | Type | Rule |
|---|---|---|
| id | Long | PK |
| currencyPairDefinitionId | Long | FK → `currency_pair_definition.id` |
| baseCurrencyCode / quoteCurrencyCode | String | Read-only enrichment (joined via the definition) |
| brandId | Long | FK → `brand.id` |
| brandCode | String | Read-only enrichment (joined from `brand.code`) |
| rate | BigDecimal | The plain rate exactly as returned by the provider — no spread, no markup, no adjustment (not rounded to the definition's `precision` either — that's a display concern, not this table's job). Identical across every brand's row for the same definition+minute |
| depositRate | BigDecimal | `rate` multiplied by `(1 + effectiveDepositSpreadPercent / 100)` using this brand's effective deposit spread percentage, computed once at sync time (see Overview) — a percentage markup, not a flat addition |
| withdrawalRate | BigDecimal | `rate` multiplied by `(1 + effectiveWithdrawalSpreadPercent / 100)` using this brand's effective withdrawal spread percentage, computed once at sync time |
| rateMinute | String (ISO datetime, minute precision, e.g. `"2026-08-25T14:23:00"`) | The sync time truncated to the minute |
| source | String | Provider identifier, e.g. `"open.er-api.com"` |
| createdAt / updatedAt | Timestamp | System maintained |

### API Contract

**GET /api/exchange-rates/latest**
- Query param (optional): `brandId` — when present, scopes the result to that brand only; `400` if it doesn't reference an existing brand.
- Returns one entry per `(currency_pair_definition, brand)` combination — filtered to the given brand when `brandId` is present, otherwise every existing brand — each enriched with its most recent `exchange_rate` row (max `rateMinute`) for that exact definition+brand, if any.
- Response `200`: `[ { "currencyPairDefinitionId": 1, "baseCurrencyCode": "USD", "quoteCurrencyCode": "JPY", "precision": 3, "brandId": 1, "brandCode": "au", "rate": 149.85000000, "depositRate": 149.90000000, "withdrawalRate": 150.10000000, "rateMinute": "2026-08-25T14:23:00", "source": "open.er-api.com" }, ... ]` — a definition+brand combination with no synced rate yet returns `rate: null, depositRate: null, withdrawalRate: null, rateMinute: null, source: null`.

**POST /api/exchange-rates/sync**
- No request body — this endpoint takes no parameters at all. One call syncs every definition for every existing brand; there is no per-brand sync.
- **Cooldown check runs first, before any external call**: look up `MAX(updated_at)` across the whole `exchange_rate` table (all definitions, all brands). If it exists and less than 60 seconds have elapsed since it, reject immediately — response `429`: `{ "error": "匯率同步一分鐘內僅能執行一次，請稍後再試", "retryAfterSeconds": 37 }` (`retryAfterSeconds` = seconds remaining, rounded up). No external call is made and nothing is written when this triggers.
- If the cooldown passes: group all existing `currency_pair_definition` rows by their base currency code. For each distinct base currency, call `GET https://open.er-api.com/v6/latest/{baseCode}` once. Compute one `rateMinute` for the whole sync call (current server time, truncated to the minute — every row updated by this call shares the same `rateMinute`). For each definition whose base currency's call succeeded and whose quote currency code is present in the response: for **every existing brand**, resolve that brand's currently-effective deposit/withdrawal spread for this definition's currency pair (group's if assigned, otherwise the brand's default — same resolution as [currency-pair.md](currency-pair.md)), compute `depositRate`/`withdrawalRate` from the provider's `rate`, and upsert `exchange_rate` keyed on `(currencyPairDefinitionId, brandId, rateMinute)` — update `rate`/`depositRate`/`withdrawalRate`/`source` if a row for that exact definition+brand+minute already exists, otherwise insert. If the quote code is absent from the response, skip that definition entirely (for every brand, not upserted for any of them).
- If a base currency's external call fails (non-2xx, network error, or `result != "success"`), every definition under that base currency is skipped for this sync (not upserted, for any brand); other base currencies proceed independently. If every base currency's call fails, the whole sync fails and nothing is written (so the cooldown is not started — see the DBA spec's note on `updated_at`).
- Response `200`: `{ "syncedAt": "2026-08-25T14:23:00", "updated": [ { "currencyPairDefinitionId": 1, "baseCurrencyCode": "USD", "quoteCurrencyCode": "JPY", "brandId": 1, "brandCode": "au", "rate": 149.85000000, "depositRate": 149.90000000, "withdrawalRate": 150.10000000 }, ... ], "skipped": [ { "currencyPairDefinitionId": 5, "baseCurrencyCode": "USD", "quoteCurrencyCode": "XXX", "reason": "not returned by provider" } ] }` — `updated` has up to (definition count × brand count) entries; `skipped` is definition-scoped (no `brandId`, since a definition-level skip — quote code absent, or its base currency's call failed — applies to every brand identically) and `[]` when nothing was skipped.
- Response `502` (every base currency's external call failed): `{ "error": "Failed to fetch rates from external provider" }`.
- Response `429` (cooldown active): as above.
- Not audited — applies directly, no `202`/pending-request flow.

## Implementation Details
1. `GET /latest`: `currency_pair_definition` CROSS JOIN `brand` (or filtered to one `brand_id` when `brandId` is given) LEFT JOIN to the latest-per-(definition,brand) `exchange_rate` row (e.g. `ROW_NUMBER() OVER (PARTITION BY currency_pair_definition_id, brand_id ORDER BY rate_minute DESC) = 1`), plus joins to `currency` (twice, for `baseCurrencyCode`/`quoteCurrencyCode`) and `brand` (for `brandCode`).
2. `POST /sync`: check the cooldown via `MAX(updated_at)` on `exchange_rate` (`429` and stop here if within 60 seconds) → load all `currency_pair_definition` rows (with base/quote currency codes) and all existing `brand` rows → group definitions by `baseCurrencyCode` → for each group, call the external provider once (reasonable timeout, e.g. 5s) → on success, for every definition in that group whose quote currency code is present in `rates`: for every brand, look up that brand's `currency_pair` row for this definition (for `spreadGroupId`), resolve the effective `depositSpreadPercent`/`withdrawalSpreadPercent` (group's if assigned, otherwise the brand's `brand_spread` default — the exact resolution [currency-pair.md](currency-pair.md) already implements for its own `depositRate`/`withdrawalRate`), compute `depositRate = rate * (1 + depositSpreadPercent / 100)` and `withdrawalRate = rate * (1 + withdrawalSpreadPercent / 100)` — a percentage markup, not a flat addition — then upsert `exchange_rate` keyed on `(currency_pair_definition_id, brand_id, rate_minute)` (`INSERT ... ON DUPLICATE KEY UPDATE rate = VALUES(rate), deposit_rate = VALUES(deposit_rate), withdrawal_rate = VALUES(withdrawal_rate), source = VALUES(source)`) — if the quote code is absent from the response, record one `skipped` entry for the whole definition (not one per brand) and upsert nothing for it → on a base-currency failure, record nothing for that group's definitions (any brand) and continue with the remaining groups → if `updated` ends up empty and at least one group failed, return `502`; otherwise return `200` with whatever was actually updated/skipped.
3. `rateMinute` is computed once at the start of the sync (not per HTTP call, not per brand) so every row updated by one sync shares an identical timestamp.
4. `rate` is stored exactly as returned by the provider — no rounding against the definition's `precision`. `depositRate`/`withdrawalRate` are computed once per (definition, brand) at sync time and then simply stored — no recalculation happens later, even if the brand's spread configuration subsequently changes (that's what makes this a snapshot, distinct from `currency-pair.md`'s always-current live computation).
5. The effective-spread lookup reuses the same brand_spread/spread_group resolution as [currency-pair.md](currency-pair.md) — implemented as the same query shape, not literally shared code across the two mappers, consistent with this project's existing convention of small deliberate duplication over cross-mapper coupling (see [audit.md](audit.md)'s "validation happens twice" precedent).
6. The cooldown read (`MAX(updated_at)`) and the sync's own writes are not wrapped in a way that lets two concurrent requests both pass the check and both write — a single-row advisory check is sufficient for this project's scale and matches its existing convention of keeping this kind of guard simple (no distributed lock).
7. Both endpoints are plain reads/writes — no audit submission, no approval flow.

## Acceptance Criteria
- [x] `GET /api/exchange-rates/latest` (no `brandId`) returns one entry per `(currency_pair_definition, brand)` combination across every existing brand, enriched with `baseCurrencyCode`/`quoteCurrencyCode`/`precision`/`brandId`/`brandCode`; `rate`/`depositRate`/`withdrawalRate`/`rateMinute`/`source` are all `null` for a combination never synced.
- [x] `GET /api/exchange-rates/latest?brandId={id}` scopes the result to just that brand (one entry per definition); an unknown `brandId` returns `400`.
- [x] `POST /api/exchange-rates/sync` calls the external provider exactly once per distinct base currency present in `currency_pair_definition` (not once per definition, not once per brand).
- [x] A successful sync upserts one `exchange_rate` row per (definition, brand) whose quote currency was returned by the provider — for 9 definitions × 7 brands with full coverage, 63 rows.
- [x] Every upserted row's `depositRate` equals `rate` multiplied by `(1 + depositSpreadPercent / 100)` using that specific brand's currently-effective deposit spread percentage — a percentage markup, not a flat addition (matching what `GET /api/currency-pairs` reports as that pair's live `depositRate` at the same moment); likewise for `withdrawalRate`. A brand assigned to a spread group uses the group's spread percentage; an unassigned brand uses its own default.
- [x] Two different brands with different effective spreads for the same definition end up with different `depositRate`/`withdrawalRate` in the same sync, sharing the same `rate` and `rateMinute`.
- [x] Changing a brand's spread configuration after a sync does not alter any already-written `exchange_rate` row's `depositRate`/`withdrawalRate` — only a subsequent sync produces new rows reflecting the change.
- [x] A second `POST /api/exchange-rates/sync` within 60 seconds of the last successful one returns `429` with `retryAfterSeconds`, makes no external call, and writes nothing (for any brand).
- [x] Once 60 seconds have elapsed since the last successful sync, a new `POST` succeeds again.
- [x] A sync that fails entirely (every base currency's call fails, `502`) does not start or extend the cooldown — an immediately following retry is not blocked by `429`.
- [x] A quote currency absent from the provider's response for its base currency is reported under `skipped` once per definition (no `brandId`, no per-brand duplication), and does not fail the rest of the sync.
- [x] If one base currency's external call fails, definitions under other successful base currencies are still updated for every brand; if every base currency's call fails, the endpoint returns `502` and writes nothing.
- [x] `GET /api/exchange-rates/latest` reflects a sync's results immediately after a successful `POST`.
- [x] Neither endpoint creates an `audit_request` row or returns `202` — both apply/read directly.

Root-caused and fixed by moving the elapsed-time computation entirely into MySQL (`SELECT TIMESTAMPDIFF(SECOND, MAX(updated_at), CURRENT_TIMESTAMP) FROM exchange_rate`), so both timestamps come from the same clock/timezone and are never compared cross-system.
