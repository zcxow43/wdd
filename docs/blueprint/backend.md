# 匯率中心主檔與幣種對管理 — 系統整合架構文件

## 1. 文件目的

本文件整合以下四份 backend spec，形成單一系統級大圖：

- 品牌主檔（Brand）
- 幣種主檔（Currency）
- 幣種對定義（Currency Pair Definition）
- 品牌幣種對（Currency Pair）

整合後的系統現況是：品牌與幣種是兩份互相獨立、各自維護的主檔資料；幣種對定義則以兩個既有幣種（基準幣、報價幣）組成一組「全域規格」，並在建立時自動幫每一個品牌各生出一筆屬於該品牌的「品牌幣種對」設定（目前 7 個品牌）。品牌幣種對才是真正決定每個品牌實際使用的匯率模式（自動或手動）與開關狀態的地方，而它的匯率精度規則又回頭受幣種對定義的限制。四份 spec 因此不是四個平行系統，而是一條「主檔 → 全域規格 → 品牌落地設定」的層層堆疊關係。目前系統中所有異動（新增、修改、刪除）都是直接生效，沒有任何審核／待審流程。

![Diagram 1](backend/1.png)

此圖顯示四個實體/資料儲存之間唯一存在的真實關係：幣種對定義引用幣種主檔的基準幣與報價幣；幣種對定義建立時會自動為每個品牌各建立一筆品牌幣種對（fan-out）；品牌幣種對歸屬於它所屬的幣種對定義，也歸屬於它所屬的品牌；而幣種對定義要被刪除前，必須先確認底下每一筆品牌幣種對都已經是關閉狀態。品牌主檔與幣種主檔彼此之間沒有任何關係，各自是獨立維護的主檔。

## 3. 各實體/資料儲存說明

### 3.1 品牌主檔（Brand）

<img src="backend/1-brand.png" width="320" alt="品牌模組節錄圖">

*（節錄自完整架構圖）*

品牌是整個系統中所有「品牌別設定」的擁有者根節點——品牌幣種對就是掛在品牌之下的其中一種設定。系統內建 7 個品牌（au、moneta、pug、star、um、vjp、vt），這 7 個品牌只能透過資料庫種子資料存在，不提供新增或刪除的操作介面；管理員唯一能透過介面異動的欄位是「是否啟用」。品牌的代碼與名稱一旦建立即不可更改。在整體架構中，品牌是品牌幣種對的其中一個歸屬維度，其本身則是一份獨立、單純的主檔，新增/查詢/修改/刪除各自獨立生效，沒有跨實體效應。

詳細欄位、規則與 API 定義 → docs/backend/brand.md

### 3.2 幣種主檔（Currency）

<img src="backend/1-currency.png" width="320" alt="幣種模組節錄圖">

*（節錄自完整架構圖）*

幣種主檔是系統中所有貨幣代碼（如 USD、JPY）的唯一來源，提供完整的新增、查詢、修改、刪除能力。幣種代碼一旦建立即不可更改，但名稱、符號、小數位數（精度）皆可修改。在整體架構中，幣種是幣種對定義的組成材料——每一組幣種對定義都必須引用兩個已存在的幣種作為基準幣與報價幣。幣種主檔本身也是一份獨立維護的主檔，沒有跨實體的建立/刪除限制。

詳細欄位、規則與 API 定義 → docs/backend/currency.md

### 3.3 幣種對定義（Currency Pair Definition）

<img src="backend/1-currency-pair-definition.png" width="320" alt="幣種對定義模組節錄圖">

*（節錄自完整架構圖）*

幣種對定義代表系統中「這兩種貨幣組成一組匯率」的全域規格，例如「USD/JPY」。它引用兩個既有幣種作為基準幣與報價幣（建立後不可更改），並訂定一個精度上限（可修改）——這個精度上限之後會用來限制每個品牌自行填寫手動匯率時的小數位數。幣種對定義本身沒有啟用/停用狀態；它的存在與否，直接決定底下是否存在對應的品牌幣種對。建立與刪除的邏輯都不單純：建立時會自動為每個品牌各生出一筆品牌幣種對；刪除時必須先確認底下所有品牌幣種對都已關閉。

![Diagram 2](backend/2.png)

詳細欄位、規則與 API 定義 → docs/backend/currency-pair-definition.md

### 3.4 品牌幣種對（Currency Pair）

<img src="backend/1-currency-pair.png" width="320" alt="品牌幣種對模組節錄圖">

*（節錄自完整架構圖）*

品牌幣種對是每個品牌針對某一組幣種對定義的實際落地設定，決定這個品牌現在是用自動匯率還是手動匯率、匯率值是多少、以及目前是否開放使用。多數品牌幣種對是由幣種對定義建立時自動生成的，但系統也允許針對單一品牌、單一幣種對定義直接新增或刪除一筆（例如補建一筆先前被刪除的設定）。它所歸屬的幣種對定義與品牌一旦建立即不可更改；手動匯率的數值與小數位數則受限於所屬幣種對定義的精度上限。品牌幣種對的刪除沒有額外限制——不論目前是開啟或關閉都可以直接刪除，開關限制只存在於它的上層（幣種對定義的刪除）。

## 4. End-to-End 情境走查

以下三個情境會跨越兩個以上實體，且揭露非顯而易見的業務規則；一般單一資料表的例行新增/查詢/修改/刪除步驟（屬於品牌、幣種本身的標準 CRUD）不在此重複。

### 情境一：建立幣種對定義後，自動幫每個品牌落地一筆設定

管理員新增一組幣種對定義（例如 USD/JPY）時，系統會先確認基準幣與報價幣都存在且不同。確認無誤後，系統不只建立這一筆全域定義，還會在同一次操作中讀取目前所有品牌（目前 7 個），逐一幫每個品牌建立一筆對應的品牌幣種對——這些自動生成的品牌幣種對一律是「自動匯率」、沒有填入匯率數值、狀態為關閉。回應會同時包含這筆新建的定義本身，以及底下 7 筆自動生成的品牌幣種對清單。也就是說，管理員只建立了一次「規格」，系統就自動幫每個品牌都準備好了對應的落地設定，但這些落地設定預設是關閉的，需要各品牌自行後續開啟並決定匯率模式。

### 情境二：刪除幣種對定義前，必須先確認沒有品牌還在使用

當管理員嘗試刪除一組幣種對定義時，系統不會直接刪除，而是先逐一檢查底下每一筆品牌幣種對目前是否為開啟狀態。只要有任何一個品牌的幣種對還是開啟的，系統就會拒絕這次刪除，並明確列出目前仍開啟的品牌代碼，讓管理員知道要先去把哪些品牌的設定關閉才能繼續。只有當底下所有品牌的幣種對都已經是關閉狀態時，刪除才會成功——而且刪除成功後，底下所有（此時皆已關閉的）品牌幣種對會一併被連動移除，不需要管理員再逐筆刪除。這個規則確保了不會有品牌正在使用中的匯率設定，因為上層規格被移除而憑空消失。

### 情境三：把品牌幣種對改成手動匯率，但填入的數值超出定義的精度限制

管理員針對某個品牌的幣種對，把匯率模式從自動改為手動，並輸入一個匯率數值。系統在儲存前會先回頭查詢這筆品牌幣種對所屬的幣種對定義，取得該定義訂定的精度上限（例如小數點後 4 位）。如果管理員輸入的匯率小數位數超過這個上限，或輸入的數值不是正數，系統會拒絕這次修改並說明原因，不會儲存。這說明了品牌幣種對的手動匯率並不是完全自由填寫的——它的精度受限於上層幣種對定義所訂的全域規格，而不是每個品牌各自決定。反過來說，只要把匯率模式從手動切回自動，系統會自動清空原本填入的匯率數值。
